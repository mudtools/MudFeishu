# ADR-0003：回合管线的阶段次序与补偿路径

- 状态：**已决策（次序与补偿语义冻结）**
- 日期：2026-10-14（由 `Mud.AI.Agent/Events/ConversationalTurnPipeline.cs` 的类级注释迁出）
- 影响面：`Mud.AI.Agent/Events/ConversationalTurnPipeline.cs`、`Mud.Feishu.AI/Events/*ConversationalEventHandler.cs`、
  `Mud.AI.Agent/Approvals/AgentApprovalContinuation.cs`

## 背景

回合管线是「外部事件 → 会话键 → 会话 → 上下文装配 → 模型轮次 → 落库 → 回复」的机制唯一归属。
它由产品适配层的事件处理器拆分而来，多个阶段之间存在**次序依赖**，而这类依赖一旦被"顺手优化"调换，
失败形态全是静默的（丢审批、重复回复、越权读取），因此次序与补偿语义必须写成**决策**而不是散落在代码里的散文。

## 决策

### 1. 11 阶段次序（一条不许"顺手优化"）

1. **请求准入校验**（产品策略委托）：可抛异常 fail-fast；多租户分级发生在建立会话作用域之前。
2. **会话键**：经委托构造，键命名空间治理属产品策略。
3. **遥测作用域**：键只进 Span 属性，**不进 Metrics tag**（基数控制）。
4. **会话闸门**：经委托消费，同键串行、跨键并行；本层不做超时，等待语义由闸门实现决定。
5. **取/建会话**。
6. **outbox 补发**：上一轮「已生成但未确认送达」的回复，重投递命中同一轮次时**补发而不是重跑模型**
   （省一次模型计费，且不往历史里多加一轮）。
7. **孤儿审批放弃**：位置在补发之后、模型之前——补发不调模型无需修史，而修史必须早于历史进入管线。
   不处理的后果：残留的审批请求内容会让框架的整段入站配对校验在**每一轮**抛异常（事件永久毒化循环），
   且迟到的批准会执行一轮已被用户放弃的写操作（越权方向）。
8. **下发可行性前置判定**：置于补发之后（补发不消耗模型，不该被本判定拦截）、模型调用（含上下文装配）之前。
   判定不通过即按「已消费」返回：**绝不重投递**。
9. **工具执行上下文/预算作用域**：必须在上下文装配**之前**生效——知识/引用类装配器经租户上下文切租户；
   顺序颠倒会让装配器抛错并被隔离吞为 Warning，表现为「注入模式每轮零知识注入」且仅日志可见。
10. **上下文装配**：触发文本在前、装配器片段在后；空 user 消息直接短路（见 §3）。
11. **Run / RunStreaming（含流式补偿收尾）→ 落库 → 回复**。

### 2. 四类补偿路径（不得合并或删减）

| 路径 | 触发 | 语义 |
|---|---|---|
| ① | 流式取消 | 补偿收尾（Flush）必须用 `CancellationToken.None`——补偿本身不得被取消；取消语义原样保留（重抛）。 |
| ② | 流式异常 | 同上补偿收尾后异常继续向上传播（幂等键回滚 + 重投递）。 |
| ③ | 流式成功后的落库 | 用 `CancellationToken.None`——「已送达但未落库」会与幂等回滚叠加成重复回复；失败路径**不**落库（那是 at-least-once 的重投递语义）。 |
| ④ | 补发成功后的落库 | 用 `CancellationToken.None`——补发条目已在内存中摘除，这一步丢不得，否则下一轮重投递会再补发一次（用户收到两条）。 |

补偿收尾的失败只记 Warning：**不得掩盖原始异常**（回滚与重投递语义依赖它）。

### 3. 落库/回复次序与守卫

- 非流式路径**先持久化会话、再回复**（「用户可见的重复」比「历史内部多一轮」严重）。
- outbox（下发前写待补发条目）消除的是重投递时的「重跑模型」；仅非流式启用——流式已由通道分片段送达，
  补发整段会与已送达的半截内容重复。
- **审批判定先于空回复守卫**：非流式单轮是该纪律的**唯一点**，流式 `BeginAsync` 失败的回退路径必须共用
  同一回合实现（`RunNonStreamingTurnAsync`）。否则模型已产出审批请求（工具未执行）却把空文本当普通回复 ⇒
  命中空回复守卫后按「已消费」收尾——用户收不到确认提示、宿主批准通道收不到回调、**写工具静默挂起**。
- **空用户消息守卫**：空 user 消息会被 OpenAI 兼容端点拒绝（400）且已计费，故跳过本轮模型调用。
- **空模型回复守卫**：内容过滤/推理中断时文本为空——下发空文本会让平台 API 报错 ⇒ 异常 ⇒ 幂等回滚 ⇒
  重投递重跑模型（重复计费）；此处按「已消费」处理（历史已落库，仅跳过下发）。
- **触发文本不灭失**：内建装配把 `ConversationRequest.MentionedText` 放在最前、装配器片段在后——
  每个派生事件处理器的事件触发文本**永远进得了模型**。

### 4. 产品策略零内建

多租户分级（是否允许缺失租户键、工具链与租户键的组合约束）、闸门命名、装配顺序偏好都是**产品政策**，
经 `ConversationalTurnOptions` 的委托注入；管线的机制守卫（`TurnPipeline_ShouldNotHardcodeProductPolicy`）
断言本类不含任何此类判断分支。闸门满额上抛的产品异常穿过管线原样传播（at-least-once + 幂等回滚承接）。

## 理由

- 阶段次序的每一条都对应一个**已被观测到的失败形态**（毒化循环、越权写、重复回复、静默零注入），
  而不是风格偏好；因此次序本身是决策产物，不允许在代码里"顺手优化"。
- 补偿路径的 `CancellationToken.None` 要求来自同一个推理链：补偿或持久化一旦可被取消，
  「已送达」与「已落库」之间就会出现窗口，而下游幂等回滚会把窗口放大成用户可见的重复。

## 后果

- 修改管线时必须同时更新本 ADR 与 `ConversationalTurnPipeline` 的类级注释（注释只留三铁律摘要 + 本 ADR 链接）。
- 派生事件处理器的触发文本装配、回复下发、闸门实现仍属产品侧职责，不因本次迁出而变。
- 决策记录的追溯路径：`documents/AIAgent/AI-Native-实施进度-Phase*.md` 的评审条目。
