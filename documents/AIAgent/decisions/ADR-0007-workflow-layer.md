# ADR-0007：复合工作流层走「声明式只读编排」（S-4）

- 状态：**已执行**
- 日期：2026-10-20（来源：`MudFeishu-AI-审查整改-Bug修复与功能完善方案-2026-10-16.md` §5 S-4）
- 影响面：`Mud.Feishu.AI.Tools/Internal/WorkflowTools.cs`、
  `Curation/Platform/FeishuWorkflowToolInterfaces.cs`、`Guidance/workflow.md`、
  `Affordance/workflow.*.md`、`documents/AIAgent/scope-authority.json`

## 背景

模型完成「汇总会议纪要」「生成站会日报」这类任务时，需要连续调用多个工具并把结果自行拼接。
现状是每次都由模型临场编排：步骤顺序不稳定、中间结果全量进上下文、失败后的续跑只能从头再来，
审计上也看不出「同一次任务」的边界。S-4 要求把两条固定链路收敛为 `workflow.*` 工具。

## 决策

### 1. 声明式编译期常量，不引入工作流引擎

两个工作流定义是**编译期常量**（步骤列表 + 每步的参数投影函数），执行器是普通工具处理器。
不新增进程、不引入包、不落库工作流定义——AOT 友好（无反射/动态加载），定义随工具面一起版本化。
复用的是既有工具面，而不是复制 SDK 调用：每步经 `FeishuToolRegistry` 解析同一份 `FeishuToolBinding`，
授权、审计、脱敏、结果截断零旁路。

### 2. 只读设计：刻意不含写入步骤

两个工作流都**不写任何平台数据**，也不提供「把报告写成文档」的步骤。原因：

- 写入步骤会让整条链路的风险等级从只读跃升为写类，`dry_run`、默认启用策略与宿主审批语义
  全部要重做；而「生成报告后由模型再调 `docx.*`」本来就已经是一条显式、可审计的路径；
- 报告内容含 PII 时（会议纪要），自动落盘会把「一次性上下文」变成「持久化副本」，
  放大合规面。需要落盘时应由用户显式发起，而非工作流隐式完成。

因此两枚工具在风险分级上恒为 `read`，`Source` 刻意留空（它们不直接映射 SDK 方法）。
`workflow.meeting_summary` 因报告含他人发言与待办，登记 PII 且**默认不启用**。

### 3. `dry_run` 覆盖整条链

`dry_run=true` 在依赖检查与任何嵌套调用**之前**返回步骤计划：每步的工具名、启用状态、
参数 `args_preview`（**仅字段名**，不回显参数值，避免 PII 进上下文）。它不发起任何平台请求。

### 4. `resume_token`：无状态、可校验、有界

断点续跑不依赖服务端会话：`resume_token` = Base64(UTF-8 JSON) `{v, wf, fp, done[]}`。

- `v`：版本号，未知版本拒绝；
- `wf`：工作流名，跨工作流使用拒绝；
- `fp`：输入指纹（规范化后的参数），输入变化后旧 token 拒绝——防止「续跑出另一份报告」；
- `done[]`：已完成步骤的 `{id, data}`，只接受已知步骤 id 且必须按定义顺序构成前缀；
  乱序、重复、未知 id 一律拒绝。

上限 2400 字符 / 解码后 1700 字节；超限回可读错误而不是截断（截断的 token 会静默续错状态）。
token 含中间结果，不由服务端加密——宿主若把报告视为敏感数据，应自行决定是否把它回传给模型。

### 5. 失败语义

- 依赖工具未启用：在第一步执行前返回可执行的 `policy / tool_not_allowed`，指明先启用哪个工具；
- 某步失败：把嵌套工具的错误信封原样透传（`ToolErrorFactory` + `ToolResultSanitizer`），
  并在回执中标记已完成步骤，模型可据此修正参数后用新 token 续跑；
- 工作流本身不捕获 `OperationCanceledException`，取消原样上抛。

## 后果

- 新增 2 枚只读工具（363 枚 / 34 域），无新增权限点（scope 是被编排步骤的并集）；
- 每步审计带独立 `audit_id`，一次工作流的多次调用可按 `steps[]` 归组；
- 若未来要支持写入步骤，必须重开本 ADR：届时需要重新定义风险分级、`dry_run` 与审批语义。
