**PackageReference（规划时 `Mud.HttpUtils 3.0.7`；本次验证已升至 3.0.8）而非 ProjectReference**，故 #4–#7 的删除
**不能仅凭上游版本位升到 3.0.8 就开动**，必须等引用实际指向 3.0.8（已发布，或经本地渠道可还原）。两条错误路径：

- **先删 override 而不升引用（引用仍为 3.0.7）**：基类 3.0.7 仍持有 `GetWebApi` / `GetDefaultWebApi`，

- **先升引用到 3.0.8 而不删 override**：基类成员已不存在，`override` / `new` 遮蔽落 `CS0114` 一类**编译错误**。

故「引用升级到已发布的 3.0.8」与「删除本仓 #4–#7」**必须同批落地**，任一侧单独先行都产生上述后果之一。

**裁决（2026-10-18，本方案采纳）**：`GetWebApi` / `GetDefaultWebApi` / `RegisterSwitcherFactory`
**全部移除**，#4–#7 一次性删除，**无保留项**。依据按权重排列如下。

**1. #4/#5 的移除已被上游裁决承诺，且替代路径齐备 —— 3.0.0 章的第一条理由已不成立。**

上游 3.0.0 章「明确不做」曾以「`GetWebApi` 返回**新的切换器实例**，与 `IAppScopeSwitcher`
（在当前实例上切上下文）语义不等价」为由裁定**不废弃**（上游 `CHANGELOG.md` 3.0.0 章
「明确不做（避免过度设计）」）。但：

- 该「语义无法表达」的缺口随后由上游自补的 `AppKeySwitchExtensions.SwitchToApp`（`SW-15`）
  闭合 —— 上游 `CHANGELOG.md` 3.0.0 章「不可信 appKey 的『无作用域切换』扩展」与
  `Abstractions/README.md:227-231` 明确说该扩展就是为
  「不可信 appKey + 完整守卫 + 无作用域」这一组合而生；
- 更关键：本仓 `GetWebApi` **重写后早已不是「返回新实例」** ——
  `FeishuAppManager.cs:1479-1497` 是「DI 解析 + 授权守卫 + `holder.SwitchTo(...)`，
  **切换后不归还**」，其自身 `[Obsolete]` 消息（`:1470-1472`）亦声明与 `SwitchToApp`
  **「语义等价」**。**唯一实现方已自行判定语义等价**，故理由 A 对本仓不成立。

**2. #6/#7 的移除是 #4/#5 的「蕴涵结论」，不是独立计划 —— 上游 3.0.0 章的第二条理由归于无效（moot）。**

上游 `DefaultAppManager.SwitcherFactory.cs` 的私有 `CreateContextSwitcher<TContextSwitcher>` 仅被
`GetWebApi` / `GetDefaultWebApi` 调用（同文件 `:24`、`:33`）；`RegisterSwitcherFactory` 注册的工厂
**只服务这一个消费者**。一旦 #4/#5 移除，工厂**再无任何调用方**，保留它等于保留一个
「宿主注册后永不生效」的公开 API —— 诱骗宿主以为 AOT 实例创建已接缝。故 **随 #4/#5 同批删除**。

由此，3.0.0 章的「AOT 友好实例创建的唯一接缝、无等价替代」并非被推翻，而是**随其唯一消费场景一并消失**：
本仓 `GetWebApi` 的实现本身就是 DI 解析路径（`_serviceProvider.GetService<T>()`），
AOT 场景下的切换器实例创建由 DI 覆盖。若未来出现「无 DI、需 AOT 创建切换器」的真实宿主，
应另立**对齐真实构造依赖**的新接缝，**不得**复活现存的离线 1 参委托接缝
（与生成器 3 参构造不对齐，对生成器场景本就不生效，见上游 `CHANGELOG.md` 3.0.0 章
「修复（Fixed）」的工厂指引条目）。

**3. #6/#7 在本仓的既有性质澄清（影响删除顺序）。**

它们不是「待清理的弃用遗留」，而是**保护性遮蔽**（`[Obsolete(error:true)]` +
`NotSupportedException`），用于阻止宿主注册一个会被 `GetWebApi` 忽略的工厂。
**删除前提是基类成员先消失**，否则 `new` 遮蔽一个不存在的基类成员会落 `CS0114`。
故顺序不可颠倒：**上游先发布 4.0（本仓引用随之升级）→ 本仓同批删除 #4–#7**（见本节「下游门禁」）。

**4. 移除成本：本仓是这两成员的主要文档持有者，须同批落地（非纯清理）。**

调用/展示点：`README.md:1811/1815/1891`、`README_EN.md:554/558/742`、
`Mud.Feishu/README.md:714`、`Mud.Feishu.Abstractions/README.md:390/398/494/507`、
`Mud.Feishu.Abstractions/README_EN.md:435/442`、`Demos/Mud.Feishu.Demo/Controllers/MultiApp/MultiAppControler.cs:35`、
`Tests/Mud.Feishu.Abstractions.Tests/Authentication/MultiAppTests.cs:583/640`。
生产代码**零调用**（仅文档 + 1 个 Demo + 2 处测试），故成本为机械性改写。

其中 `Mud.Feishu.Abstractions/README.md:507` 的「**推荐使用 `IFeishuAppManager.GetWebApi<T>(appKey)`
获取独立的服务实例**」是一处**必须修掉的错误安全声明**：该成员重写后写入的是同一个
`AsyncLocal` Holder，「独立实例」不成立；该「线程安全」推荐方向反而把用户引向
**会污染当前执行流上下文**的多线程用法。移除该成员同时**消除这个安全脚枪**。

### 档 C —— 纯本仓自主族（#1–3、#8、#10–13、#15–21）

**关键澄清（§1 中 #1–3 的「下一个大版本才可删」不是生成器依赖）**：

上游 `BC-27` 在接口侧移除这三个成员时，保留了一个「**声明 ⇒ 发射**」豁免——使用方接口若自己声明

188+ 生成类照常编译。

生成类落入 `HTTPCLIENT024`（Error）占位。

## 5. 风险清单

1. **#1–3 的两个反向误判**：既不能「等上游解锁」而长期冻结（上游无此依赖），也不能在保留期内改动
   签名（豁免失效 ⇒ `HTTPCLIENT024`（Error）⇒ 188+ 生成类编译失败）。
2. **#10 / #11 的守卫改靶**：I14 是源码文本级断言，删方法后不改靶会丢失「接收循环唯一性由原子占位
   保证」这条 P0 防线。
3. **#18 / #19 是行为变更而非死代码清理**：#19 删除后若不迁位，重放窗口不变量会从「启动期强制」
   退化为「仅文档」。
4. **#12 / #13 涉及安全默认**：删除前须确认自签名放行仍只由 `Mode=Dev` 开闸。
5. **#14 的真正难点是公开属性改型**（`FeishuWebSocketOptions.EventDeduplication`），比删类型更难，
   必须作为独立破坏项公告。
6. **R5.6 门禁同批纪律**：删键与键名模式化锁定必须同阶段落地，否则出现「删了键但门禁不拦回归」窗口。
7. **上游 3.0.8 窗口错位（已消解）**：上游于 2026-10-18 完成 `BC-30` 物理移除（版本位 `3.0.8`），
   本仓经**本地渠道**（`pack_debug` → `artifacts-debug` + 缓存同步）消费 3.0.8 并**同批**删除
   #4–#7，验证通过（见 §2 档 A「本地验证」）。**上游已于 2026-10-18 发布 `3.0.8` 到 nuget.org，
   `nuget.config` 的本地源已移除**；此后回归风险仍为：引用若在无本地源时回落 3.x，删除动作会静默
   丢掉 fail-closed 授权守卫（安全事故）。共释协议见上游方案 §4。
