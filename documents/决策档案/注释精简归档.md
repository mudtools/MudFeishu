# 注释精简归档

按规范 §8.3「先归档、后精简」，本文件承接从源码 `<remarks>` 中移出的论证——
它们不是契约（消费者不需要），也不是维护者无法推断的约束，而是**为什么这样设计**的理由。

每条记录格式：`<文件> · <成员>` → 移出内容 → 现源码保留的契约。

## `Mud.Feishu.Abstractions/Authentication/MultiApp/FeishuAppManager.cs` · `GetWebApi<T>`

**移出内容**：

1. **DI 解析模式 vs 基类工厂委托模式**的取舍说明——本方法只走 DI 路径，
   `RegisterSwitcherFactory` 注册的工厂不会被使用；统一为 DI 模式是为降低理解成本。
   （基类工厂委托路径本身已 `[Obsolete]`，见 `迁移与弃用史.md`。）
2. **守卫口径的逐条展开**（bullet 列表）：appKey 格式校验 → 未注册授权器默认拒绝 → 授权判定；
   三条异常消息与生成代码逐字一致，由上游 `AppKeyGuardConsistencyTests` 跨项目钉死。
3. **解析器同源**：生成类在 TokenManager 模式下的 `_tokenManager` 即 `IFeishuAppManager`（本类单例），
   故两者的 `GetApp(appKey)` 命中同一注册表。
4. **`AsyncLocal` 并发与注册建议**：`IAppContextHolder` 基于 `AsyncLocal<T>`，
   即使 `T` 注册为 Singleton，并发切换也不会互相覆盖（每个异步流持有独立 `Current` 值）；
   但仍建议把 `T` 注册为 Scoped（`AddFeishuApi<T>` / `AddFeishuApp<T>`），
   避免 Singleton 实例长期持有已释放的 `IFeishuAppContext` 引用。

**现源码保留**：无作用域切换语义（切换后不归还，`Current` 即目标应用）、守卫与生成实现逐字等价、
Holder 为 DI 单例故切换对全部消费者可见、已弃用与迁移方向。

## `Mud.Feishu.Abstractions/Authentication/TokenManager/FeishuTokenStoreCodec.cs` · 类型级

**移出内容**：**回滚代价（须知）**——回滚到 3.0.2 及更早的二进制时，新格式值的前导数字会被旧解析
当作毫秒戳（远小于当前时刻）→ 判为已过期 → 未命中 → 重新获取令牌；Redis 侧 refresh 键会被旧
`SetRefreshTokenAsync` 的「已过期删键」逻辑删除（用户需重新授权）。不产生错误令牌，
但升级 / 回滚不对称——发布前请评估回滚窗口。

**归档原因**：属版本迁移史（L3），描述的是"旧二进制会怎样"，不是当前契约。

**现源码保留**：薄包装定位（双读归官方 `MigrationTokenStoreCodec`，不得再写私有双读）、
写入格式单写相对秒且与官方 `DefaultTokenStoreCodec` 逐字节一致、互操作锚点与
"两种 `ITokenStore` 约定不可互换直插（双重编码）"。

**附注（阈值口径）**：双读判别的量级分界由官方 `MigrationTokenStoreCodec` 承担，
其默认常量写作 10<sup>11</sup>（XML 注释里写 10<sup>10</sup> 属上游文档笔误）；
本仓显式传入飞书阈值 10<sup>10</sup>，两阈值在两种真实存储形态下等价。

## `Mud.Feishu.Abstractions/Configuration/FeishuAppOptions.cs` · `EnableConfigReload`

**移出内容**：

1. **默认值的决策理由**：热更新是正确性收益（避免"以为改了配置却仍走旧配置"），
   且当时本项目尚无需要保持的存量行为；如需回滚显式置 `false` 即恢复"配置变更需重启"的旧语义。
2. **`BaseUrl` / `TimeOut` 热更新的实现链路**：命名客户端的注册委托捕获的是注册期快照，
   故 `AddFeishuAppBaseServices` 额外通过 `IHttpClientBuilder.ConfigureHttpClient(IServiceProvider, HttpClient)`
   追加 DI 感知的配置动作，在每次 `CreateClient` 时从 `IOptionsMonitor<List<FeishuAppConfig>>`
   读取**当前** `BaseUrl` / `TimeOut`，检测差异时覆盖新客户端的 `BaseAddress` / `Timeout`。
   配合「上下文重建 → 新建 `TokenRecoveryEnhancedClient` → 重新 `CreateClient`」链路，
   多区域切换（feishu.cn ↔ larksuite.com）与超时调整无需重启进程；
   在途请求仍持有旧客户端实例（其 `HttpClient` 已固化旧基地址），自然完成收敛。

**现源码保留**：订阅 `OnChange` 后的增量应用语义与默认值 `true`、`BaseUrl`/`TimeOut` 经 DI 感知动作
在每次 `CreateClient` 取当前值、生效范围（仅 `IConfiguration` 绑定才有变更通知）。

## `Mud.Feishu.WebSocket/Handlers/ScopedFeishuEventHandlerFactory.cs` · 类型级

**移出内容**：Captive Dependency 缺陷复盘——此前 `IFeishuEventHandlerFactory` 注册为 Singleton，
工厂委托直接从**根容器**解析注册为 `Scoped` 的 `IEnumerable<IFeishuEventHandler>`。后果分两档：

1. `EnvironmentName=Development`（默认开启 `ValidateScopes`）下抛
   `InvalidOperationException: Cannot resolve scoped service ... from root provider`，**应用启动失败**；
2. 非 Development 下不报错，但处理器实例被单例永久持有；处理器若依赖 `DbContext` 等 Scoped 服务，
   会出现跨事件共享实例、连接泄漏与并发访问异常。

**现源码保留**：分发路径每次调用创建并释放 `IServiceScope`（Scoped 依赖生命周期与单个事件对齐）、
查询类 API 复用惰性长期作用域、以及"不得在根容器解析处理器（`ValidateScopes` 下启动即失败）"这条约束。

## `Mud.Feishu.Redis/Services/PerAppRedisTokenStoreFactory.cs` · 类型级

**移出内容**：缺陷复盘叙述——前身 `SingletonFeishuTokenStoreFactory` 忽略 `appKey` 返回共享
`RedisTokenStore` 单例，其键布局 `feishu:token:{tokenType}:access` /
`feishu:token:user:{userId}:{tokenType}:access` 均不含 appKey 维度（含旧键形态列举与
「令牌串号」的现象归因）。

**现源码保留**：每个 appKey 独立键前缀 `feishu:{appKey}:token`、与 Memory 路径
（`FeishuTokenStore` / `FeishuUserTokenStore`）键布局逐字节一致、无 appKey 维度的键空间会
导致令牌互相覆盖（随机 401 / 令牌串号）、全部实例共享同一 `IConnectionMultiplexer`（不膨胀连接池）。
