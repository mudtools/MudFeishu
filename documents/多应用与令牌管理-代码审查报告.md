# 多应用与令牌管理域 — 代码审查报告

> **审查范围**：`Mud.Feishu.Abstractions/Authentication/`（多应用 + 令牌管理）、`Mud.Feishu.Redis/Services/`（Redis 令牌存储）、`Mud.Feishu/Extensions/`（DI 接线）、组件 `Mud.HttpUtils`（基座消费）
> **审查日期**：2026-09-23
> **审查方法**：全量阅读在册源文件（非抽样），逐条比对 9 维度（并发/竞态、多应用键隔离、令牌生命周期、组件交叉校验、安全/凭据泄露、AOT/多 TFM、API 设计/DI、性能/资源、测试覆盖）
> **组件版本**：`Mud.HttpUtils` 2.0.7（nuget.org）

## 一、总体结论

| 级别 | 数量 | 说明 |
|------|------|------|
| **P0（阻塞发布）** | **0** | 无 |
| **P1（显著缺陷）** | **0** | 无 |
| **P2（测试缺口 / 改进项）** | **4** | 均为测试覆盖缺口，非代码缺陷 |

**发布判定**：**可发布**。多应用与令牌管理域的代码质量高于一般生产标准。历史 P0/P1 问题（TOK-1 键碰撞、TMA-01 失效不级联清库、D9 恢复阈值减半、D10 凭据变更不清库、D11 refresh token 不可达、D12 OAuth 错误未分类、TMA-15 无过期信息误恢复、TMR-P3-16c 解密失败脏键残留等）均已正确修复，且每处修复都带有内联文档标注修复 ID 与不变式理由。代码中未发现新的并发竞态、键隔离破坏、凭据泄露或资源泄漏。

**核心架构评价**：
- **键布局单一真相**（D8）：`TokenKeyBuilder` 是所有令牌键的唯一出口，Memory 与 Redis 两条后端路径逐字节一致，含 glob 元字符转义（`* ? [ ]`）与段长度保护。
- **凭据变更清库**（D10）：`TokenStorePurgeGate` 以「打门 + 引用计数 + 安全超时 fail-open」实现非阻塞的「清库完成前不得恢复旧令牌」约束，避免了在 `IOptionsMonitor.OnChange` 回调线程上同步阻塞。
- **refresh token 可达性**（D11）：`LoadRefreshCandidateAsync` 独立于 access token 的存在性，access 过期后仍可续期。
- **加密装饰器**（ENH-1/ENH-2）：`EncryptedTokenStore` / `EncryptedUserTokenStore` 透明加解密，解密失败按「未命中」返回 null 并尽力删除脏键，节流告警。

## 四、误报清理区

> 以下为审查中识别的「看似缺陷、实为已正确处理」的项，列出以避免后续审查重复标记。

| 编号 | 检查点 | 结论 | 证据 |
|------|--------|------|------|
| F-1 | `TokenStorePurgeGate` 为进程内静态状态，多实例部署时其他实例仍可能恢复旧令牌 | **非缺陷**（已声明） | `TokenStorePurgeGate.cs:40-43` 注释明确：「门为进程内状态；其他实例在窗口内仍可能恢复旧令牌，与既有 Redis SCAN 的固有残余窗口同级，不构成回归」。多实例清库依赖 Redis SCAN，本就有残余窗口。 |
| F-2 | `UserTokenManager.TryRestoreFromUserTokenStoreAsync` 恢复令牌 `IssuedAt = 0` | **非缺陷**（已声明的保守 trade-off） | `UserTokenManager.cs:509-514` 注释明确（TMF-06 方案 A）：存储格式 `{expire}|{token}` 不含签发时间，`IssuedAt=0` 使组件 TTL 感知阈值退化为纯配置阈值。默认配置（TTL 7200s ≫ 阈值 300s）下判定结果与 TTL 感知完全一致；短 TTL 部署不应依赖跨重启的 store 恢复。 |
| F-3 | `FeishuUserTokenStore.SetRefreshTokenAsync` 硬编码 30 天 TTL | **非缺陷**（IMemoryCache 路径无过期信息可用） | `FeishuUserTokenStore.cs:96-113` 注释明确（TMA-22 / TMA2-15）：IMemoryCache 的 `SetRefreshTokenAsync` 重载不接收 `expiresInSeconds` 参数，保持 30 天默认。Redis 路径在 `RedisUserTokenStore` 中从编码值推断 TTL。 |
| F-4 | `FeishuAppTokenManagerBase.InvalidateTokenAsync` 先清 store 再调 base，store 清理失败被 catch 吞没 | **非缺陷**（设计意图） | `FeishuAppTokenManagerBase.cs` 中 `InvalidateTokenAsync` 的 catch 块记 `LogWarning` 后继续调 `base.InvalidateTokenAsync`——store 清理失败不阻断内存失效（内存令牌仍被清除，下次取令牌走 API 刷新，新令牌会覆写 store 旧值）。非吞没，是降级。 |
| F-5 | `UserTokenManager.RefreshUserTokenAsync` CAS 比较失败时跳过清库 | **非缺陷**（保守 trade-off） | `UserTokenManager.cs:264-272` 注释明确（TMF-05）：宿主直调（绕过组件 `KeyedLockTable`）场景下，CAS 比较失败说明 store 已被并发刷新写入新令牌，跳过清库避免误删。已知保守代价：Feishu 复用旧 refresh_token 且两次持久化时间戳不同时会跳过清库（活性损失，非正确性问题）。 |
| F-6 | `TokenKeyBuilder.BuildKeyPrefix` 不预转义 appKey | **非缺陷**（避免二次转义） | `TokenKeyBuilder.cs:252-281` 注释明确（TMR2-P1-2）：预转义会导致键构造路径二次转义（`\` → `\\`），Redis glob 把 `\\` 解释为单个反斜杠，与键不匹配，`ClearAsync` 永不命中。转义单点归口 `NormalizePrefix → NormalizeSegment`。 |
| F-7 | `EncryptedTokenStore` 解密失败时 `RemoveAsync` 脏键删除用调用方 `CancellationToken` | **非缺陷**（非补偿操作） | `EncryptedTokenStore.cs:140-147` 的脏键删除是「尽力」清理（best-effort），非 D15 定义的补偿性去重操作。脏键不删的后果是下次读取仍解密失败并重试删除，无正确性影响。 |

## 六、改进建议（非缺陷）

| 编号 | 建议 | 依据 | 优先级 |

| S-1 | `UserTokenManager.TryRestoreFromUserTokenStoreAsync` 的 `IssuedAt=0` 保守 trade-off（TMF-06 方案 A）在短 TTL 用户令牌部署下会使缓存永不命中。若未来支持短 TTL 场景，考虑升级存储格式为 `{issuedAt}|{expire}|{token}`（方案 B），使 `IssuedAt` 可从 store 恢复。 | `UserTokenManager.cs:509-514` 注释 | 低（当前默认配置不受影响） |
