# AI 工具描述符诊断（MUDFTxxx）Warning 基线 —— R5 / B-11
#
# 用途：MUDFT009（output_schema 深度截断）与 MUDFT021（参数可空性存疑）是 Warning 级，
# 天然 >0（全量消除不现实且无收益），因此**不能**断言绝对 0，改为"基线 + 拦增量"：
#   实际计数 > 基线 ⇒ 门禁红（说明新增了截断/可空性疑点，须显式评审并更新本文件）。
#   实际计数 < 基线 ⇒ 通过（变好不阻塞）。
#
# ── 测量协议（必须是这一条，否则读数无意义）────────────────────────────────
#   命令：dotnet build Mud.Feishu.slnx -c Release --nologo --no-incremental
#   计数：scripts/diagnostics-gate.ps1 的 Measure-Mudft（`(warning|error) MUDFT0xx:` 出现次数）
#
#   ⚠️ **必须带 --no-incremental**：MUDFT 诊断全部由源生成器产出，而增量构建会整体
#      跳过生成器 ⇒ 日志里一条诊断都没有 ⇒ 一切断言在"0 个诊断"上通过。
#      实测（2026-10-07，同一次改动）：增量构建 MUDFT009 = 0，全量构建 = 8。
#      CI 在全新 runner 上构建（必然全量）⇒ 基线必须按全量口径取。
#
#   ⚠️ **计数是"编译次数 × 问题条目数"**：MUDFT009 是**聚合单条**诊断（每个编译单元
#      只报一条，内含"被截断的工具数"），故 8 = 1 条 × 8 次编译（4 个 TFM ×2 类引用集）。
#      这意味着：对聚合类诊断，本机制实际退化为**二元开关**（0 / 非 0），
#      截断工具数从 30 涨到 40 **不会**让它变红。
#      ⇒ 见 S-23：要真正拦增量，须让诊断携带**机器可读的计数**并由门禁解析，
#         或把断言移到"生成器驱动的测试"（确定性、与增量/编译次数无关）。
#
# 数据来源：2026-10-07 Release **全量**构建实测（协议见上），工具面 87 个。
#   009 的语义量（诊断消息内）：**30 个工具**的 output_schema 在深度上限 4 内被截断
#   （SDK 中存在天然超过 4 层的 DTO；代码注释亦自述"必然存在深层 DTO"——
#     故此处**不得**再写 0，那只能是"生成器被跳过"导致的假读数）。
#
# 格式：
#   <三位ID>=<允许的最大计数>                 ← 日志出现次数口径（Measure-Mudft）
#   <三位ID>-tools=<允许的最大工具数>          ← **语义量**口径（仅聚合单条诊断需要，见 S-23）
# 行首 # 为注释。
# 口径与 ID 清单的单一真相源在 scripts/diagnostics-gate.ps1（$MudftBaselineIds 引用本文件）。
#
# ── 为什么 009 需要第二套口径（S-23）────────────────────────────────────────
#   MUDFT009 是**聚合单条**诊断：每个编译单元只报一条，真正的计数写在**消息文本**里
#   （"N 个工具的输出 Schema 被截断"）。所以 `009=8` 里的 8 是"1 条 × 8 次编译"，
#   **截断工具数从 30 涨到 40 时它不变** ⇒ 光靠出现次数，这条基线拦不住它本该拦的增量。
#   故补 `009-tools=30`：按消息里的工具数断言（编译无关、与增量构建与否无关），
#   由 verify-build.ps1 与 CI workflow 共同断言（Get-MudftSemanticBaseline /
#   Get-MudftOutputSchemaTruncatedToolCount）。

009=8
009-tools=30
021=0
